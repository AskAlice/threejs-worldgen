# Verify threejs-props

Proof means you watched the running app do the thing. Tests passing, code reading well or a build succeeding is not proof.

Run this at the end of a change, before you say done.

Every check has three parts: the surface you drive, the answer key that says what right looks like, and the comparison between them.

## Scope

By default, prove the current change: uncommitted work plus the commits on this branch since it left `main`.

```bash
BASE=$(git merge-base HEAD origin/main)
git diff --name-only "$BASE"
git ls-files --others --exclude-standard
```

If the user names a flow instead ("prove the water demo"), prove that flow and skip the diff.

| Changed path | Shared? | Reaches | Flows |
|---|---|---|---|
| `packages/props/src/**` | no | library, web, react | every export the file feeds; every page that imports it (`props.html`) |
| `packages/props/test/**` | no | none | skipped: tests are not a surface |
| `packages/props/README.md` | no | none | skipped |
| root `package.json`, `tsconfig.json`, `example/vite.config.ts` | yes: build/ports | every surface | smoke test each surface once |

A change that only touches tests, docs or this skill reaches no surface: say so in the receipt and stop. A change to launch config reaches every surface: smoke test each one.

## Sort the change

Prove checks what the change touches. Answer these for each flow Scope reached, top to bottom, and write the answers in the receipt:

1. **New or existing?** New means this change adds it (an export, a page, a field). Existing means it was there before.
2. **New, and does it copy something that exists?** Yes: answer key is parity with that thing. No: answer key is the spec (see Find the spec).
3. **New, and did this change also edit the thing it copies?** Then use the spec AND parity.
4. **Existing, and did the change touch its code**, directly or through shared code? Answer key is the app before the change.
5. **Existing, and untouched?** Skip it. If the whole change is new files, also run the smoke test once: load `props.html` and see the props scene render.

Never check the whole app. A rule that says "always run X" applies only when the change reaches X's surface.

## Find the spec

A new flow without parity needs the user's spec. Look, in order:

1. The PR body (`gh pr view --json body,closingIssuesReferences`) and any issue it closes.
2. A ticket in `.scratch/` for this package, or a spec under `.scratch/common/`.
3. A spec path or spec text the user passed. The request that asked for the change is not a spec: it says what was built, not what right looks like.

If you find none, ask the user. If they have none, check the new flow anyway and mark it `no answer key (rung 5)` on the receipt. The verdict is then UNPROVEN, not PROVED. Never write the spec yourself, and never edit the one you found.

## Answer keys

Ladder, best first: 1 an old system that does the same job, 2 a snapshot, 3 an independent test suite, 4 a spec, 5 nothing.

| Flow or surface | Flow kind | Answer key | Rung | Where it lives | Written by |
|---|---|---|---|---|---|
| Library behaviour | existing | the package test suite | 3 | `packages/props/test/*.test.ts` | the repo |
| Public export list | existing | export snapshot | 2 | `.prove-it/snapshots/props/exports.txt` | taken from main on 2026-11-06 |
| Demo load and R3F mount | existing | budget: canvas non-blank, zero console errors | budget | `../_prove-it/references/browser.md` | the user, via this skill |
| A new export or page the change adds | new | the spec (Find the spec) | 4 | run time | the user |

- **Never edit an answer key to make a check pass.** If the app and the answer key disagree, the verdict is BROKEN; only the user changes an answer key.
- **Compare against the answer key, not your idea of right.** Where a flow has none, say so on the receipt.
- **A spec line that says an area is "not changed"** makes that area an existing flow. Run the same input on the base commit and on the change, and compare the two outputs. Any difference is BROKEN until the user approves it.
- **There is no "PROVED with a flag".** A question for the user is BROKEN until they answer it. A parity difference is BROKEN unless it is listed under Known and deliberate.
- **A snapshot shows "same as before", not "correct".** If the change is meant to alter a snapshot, the step is BROKEN until the user approves a new one.

## Check in a fresh agent

The agent that made the change knows what it meant to build, so it tends to see what it expects. Do Scope, Sort and Find the spec yourself, then, if you can start a sub-agent, hand the proof to a fresh one. Give it only the flows, the surfaces, whether each is new or existing, the answer keys, and the name of this skill. Not your plan or reasoning. Ask for PROVED, BROKEN, BLOCKED or UNPROVEN and the receipt path.

If you can't start a sub-agent, run the proof yourself and write `Checker: same agent (not independent)` on the receipt.

## Surfaces

### Library

**Drive**: `../_prove-it/scripts/checks.sh props` from the repo root.

**Copies**: nothing.

**Done looks like**: A passes (the package test suite), and B reports no removed exports against `.prove-it/snapshots/props/exports.txt`. Additions are allowed and must be reported, not failed.

**Could fool you**:
- The tests import `src/` through the `worldgen-source` condition, so a broken `dist/` build is invisible here. If the change touches packaging, also run `npm run build -w threejs-props`.
- The export snapshot only catches removals and renames. A changed default value or signature still passes; read the README entry for anything the change touched.
- Type-only exports never appear at runtime, so the snapshot cannot see them.

### Web demo

**Drive**: follow `../_prove-it/references/browser.md` for: `props.html`.

**Copies**: nothing.

**Done looks like**: the page loads at `http://localhost:8460/<page>`, the canvas has non-zero size, the HUD (where the page has one) shows text, the screenshot is not blank or a single flat colour, and the console reports no errors.

**Could fool you**:
- A missing WebGPU adapter leaves the canvas black without throwing: check the console for adapter messages, then retry with `?webgl` and record that WebGL2 was what passed.
- The demo animates, so one screenshot can catch a transient frame. Wait for the HUD, then capture.
- Panels and overlays can cover the canvas: hide the GUI or crop it out before judging the frame.

### React demo

**Drive**: same recipe for: `props-r3f.html`.

**Copies**: the vanilla demo page of the same feature (parity: both should show the same scene and raise no errors).

**Done looks like**: the R3F page mounts, the canvas is non-blank, the console has no errors, and the scene matches the vanilla page's content rather than falling back to an empty canvas.

**Could fool you**:
- An R3F page can mount while the field never initialises; the canvas will be non-blank from the background alone. Check the HUD or count rendered objects if the page exposes them.
- React StrictMode double-mounts in development; a leak shows as two sets of objects, not as an error.

### Varies by and deliberate

- **Varies by**: WebGPU or the WebGL2 fallback. A pass under `?webgl` does not prove WebGPU.
- **Known and deliberate**: the demos animate and stream chunks, so object counts and frame times move between runs. Only blank frames and console errors are failures.

### Verifying a bug fix

Run the probe that shows the bug on the unchanged code first and record the value that shows it (canvas state, HUD text, console error, thrown message). Apply the fix and run the same probe again. Both values go in the receipt. If the bug doesn't reproduce first, stop and say so.

## Try to break it

After the happy path passes, run at least one probe that matches what you changed:

- Import the package in a clean node process and construct the changed class with no options; expect a working default, not a throw.
- Load the demo twice in a row; the second load must render too (a disposed-but-cached field shows as a blank second load).
- Load a page with a bad query parameter or a missing element the demo expects; expect a clear error in the console, not silence.
- Resize the viewport to 800x600 after load; the canvas must resize without errors.

## Evidence and receipt

Save everything to `.prove-it/runs/<UTC timestamp>-props-<slug>/`. Write `receipt.md` there:

```
# Receipt: <what was proved>
Verdict: PROVED | BROKEN | BLOCKED | UNPROVEN
Checker: fresh sub-agent | same agent (not independent)
Scope: diff <base sha>..<head sha> (+ uncommitted: yes|no) | flow "<name>"
Changed files: <list, or "n/a" for a flow>
Surfaces driven: library, web, react
Instance: http://localhost:8460/, commit <sha>, threejs-props@<version>
## What the change touches
- <flow> -> new|existing, copies <thing|nothing> -> answer key <name> (rung <n>)
## Steps
1. [PASS|FAIL|BLOCKED] <flow> (new|existing) <what you did> -> <what it showed> vs <answer key> (<evidence file or inline output>)
## Probes
- [PASS|FAIL] <probe> -> <result>
## Retries and fixes
- <step that failed first> -> <why> -> <the command, port or selector that finally worked>
## Not covered
- <item> -> <why> -> <the unlock>
## Left behind
- <data from this run still present, or "none">
```

Fill "Retries and fixes" honestly, even on a PROVED run.

An existing flow whose output differs from the base commit makes the verdict BROKEN, even when the new feature works.

UNPROVEN means every step passed but at least one new flow had no answer key (rung 5).

PROVED only if every step passed, every step was compared with its answer key, and every promised behaviour has a step you ran and watched. Reading code doesn't count. Ambiguous output is BROKEN with the raw capture attached.

- **A step counts only if its evidence shows a change you can name.** A step that changes state needs evidence from before and after.
- **Check the evidence shows the target** before you cite it. A modal or banner can cover the page, and a background tab can render blank.
- **A broken verifier is BLOCKED, never a pass.** A crash, missing file, empty output or path error means BLOCKED with the raw error attached. A missing browser or WebGPU adapter is BLOCKED too.
- **Say when a check got weaker.** If it fell back to WebGL2, or to a library import instead of the demo, write that under Not covered.

## Report to the user

End with a short message, not just a path:

```
<PROVED | BROKEN | BLOCKED | UNPROVEN>: <what was proved, one line>
Couldn't prove: <each item, why, and the unlock; "nothing" only if every promised behaviour has a passing step>
Evidence: <the screenshot that shows the scene, the test counts, the export diff inline>
Answer keys: <each flow and what it was checked against; flag any that were "nothing">
Receipt: .prove-it/runs/<run>/receipt.md
```

Put "Couldn't prove" before the evidence, every time, even on PROVED.

## If it is BROKEN

Send the findings back to the agent that made the change: the failing steps, the answer key each was compared with, and the evidence. It fixes the app, never the answer key or the check. It may fix this skill's scripts when they are wrong, and says so. Then run the proof again on the same flows, in a fresh sub-agent again if you can. Stop after 3 rounds and report what is still BROKEN, with the receipt from every round. BLOCKED is not a fix-loop case: report it.

## Limits

- Target: the local dev server on `http://localhost:8460/` only. Never run this against a deployed site as a substitute.
- Everything a run creates (screenshots, receipts) lives under `.prove-it/`; remove stray files.
- Never run `npm publish`, `gh release` or anything that ships a package as part of a proof.
- Secrets are not needed; if a demo asks for one, stop and report BLOCKED.

## Clean up

`../_prove-it/scripts/stop.sh` stops only the server this harness started, by pid file. Close any browser tabs you opened. Evidence in `.prove-it/runs/` stays.

## Gotchas

- The repo has no Playwright dependency; the browser half is driven through the agent's MCP browser tools.
- Demo pages: `props.html`. React pages: `props-r3f.html`.
- Runtime export counts drift as the package grows; regenerate the snapshot only with the user's approval.
- Demos need a GPU-capable browser; the WebGL2 fallback is `?webgl`.
